# gp-to-hive-etl-migration

Демонстрационный проект: перенос ETL-загрузки с источника в Greenplum на источник в Hadoop/Hive. Результат загрузки остаётся прежним: данные попадают в ту же буферную таблицу PostgreSQL, а следующий DAG запускается так же, как раньше.

## Что показывает проект

- Замену источника данных без изменения интерфейса для остальной системы.
- Запуск Spark-приложения из Airflow DAG вместе с пакетом собственного кода.
- Перенос SQL-логики в PySpark: фильтрация актуальных записей, исключение технических позиций, приведение набора колонок к контракту таблицы.
- Безопасный повторный запуск: перед записью удаляются строки той же даты.
- Запись результата в PostgreSQL по JDBC.
- Хранение подключений вне кода: параметры берутся из Airflow Connections во время запуска.
- Шаблон SQL-сверки для сравнения старого и нового источников.

## Идея миграции

```text
Было:    Greenplum -> перенос данных -> буферная таблица PostgreSQL -> следующий DAG
Стало:   Hive -> PySpark-приложение -> буферная таблица PostgreSQL -> следующий DAG
```

## Структура репозитория

| Путь | Назначение |
|---|---|
| `dags/catalog_load.py` | Airflow DAG: очистка даты, запуск Spark, запуск следующего DAG |
| `jobs/catalog_job.py` | Spark-приложение: чтение Hive, преобразование, запись в PostgreSQL |
| `catalog_etl/transform.py` | Преобразования данных на PySpark |
| `catalog_etl/config.py` | JDBC-настройки из переменных окружения и проверка даты запуска |
| `scripts/build_package.py` | Сборка `dist/catalog_etl.zip` для передачи в Spark |
| `sql/reconcile.sql` | Шаблон проверки: количество строк, уникальные ключи, пустые значения |
| `tests/` | Тесты конфигурации, сборки пакета и преобразований |
| `requirements.txt` | Зависимости |

## Как работает загрузка

1. DAG `update_catalog_items` запускается каждый день в 07:20.
2. Задача `clear_run_date` удаляет из `buf.catalog_items` строки с `load_date`, равной дате запуска.
3. Задача `load_items` запускает Spark-приложение через `SparkSubmitOperator`. Пакет `catalog_etl.zip` передаётся параметром `py_files`.
4. Приложение читает `catalog.dim_item`, оставляет актуальные записи (`valid_to_dttm` равно условной «бесконечной» дате), исключает технические позиции и некоторые группы товаров, добавляет колонку `load_date`.
5. Результат записывается в `buf.catalog_items` по JDBC.
6. После успешной загрузки DAG запускает `build_catalog_marts`.

Все названия таблиц, колонок и групп вымышленные. Колонка `load_date` добавлена в демо ради повторных запусков, у реальной таблицы структура может отличаться.

## Подключения и секреты

В репозитории нет паролей, ключей и реальных адресов. Используется подключение `pg_buffer` из Airflow Connections. Его значения подставляются при запуске и передаются приложению через переменные окружения `PG_HOST`, `PG_PORT`, `PG_DB`, `PG_USER`, `PG_PASSWORD`. Если параметра нет, приложение останавливается с понятной ошибкой до подключения к базе. Для реального окружения такие значения лучше хранить в secrets backend.

## Как подготовить запуск

```bash
python scripts/build_package.py
```

Команда создаёт `dist/catalog_etl.zip`. Скопируйте архив и `jobs/catalog_job.py` в каталог, указанный в DAG (`/opt/airflow/jobs`), и создайте в Airflow подключения `spark_default` и `pg_buffer`.

## Проверка корректности миграции

Шаблон `sql/reconcile.sql` нужно выполнить для старого и нового источников и сравнить результаты: количество строк, уникальные ключи, пустые значения. Это быстрая проверка, а не доказательство полного совпадения данных.

## Запуск тестов

```bash
python -m unittest discover -s tests -t .
```

Тест преобразований требует установленного PySpark, без него он пропускается. Для запуска самого DAG нужны Airflow, Spark, Hive и PostgreSQL.

## Версии

Рекомендуемые версии (проверьте на своём окружении): Python 3.7, PySpark 2.4.4, Apache Airflow 2.6.3 с провайдерами Spark и Postgres.

## Ограничения

- Проект не запускался целиком в связке Airflow, Spark, Hive и PostgreSQL.
- Очистка даты и запись выполняются отдельными шагами и не образуют одну транзакцию. Если запись прервётся, повторный запуск заново удалит и загрузит данные этой даты.
- Сверка источников выполняется вручную по шаблону SQL.
- Проект показывает подход к миграции, а не готовое решение для промышленной эксплуатации.
